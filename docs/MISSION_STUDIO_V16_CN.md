# Atlas V1.6｜从全球 AI 资源目录到可解释的工具选型与实施蓝图

## 为什么要做这项产品升级

早期 AI 能力图谱已经有约 5,000 条候选目录、133 个编辑精选、Top 30 官方 README/文档研究，以及若干真实隔离 SDK 和第一方合成样例。但**可运行的合成演示不等于可以满足真实用户需求的 AI Agent**。V1.6 不再继续增加同类演示，而是集中解决一个真实问题：**面对具体业务任务，应该先研究哪些开源项目、为什么、有什么阻断、如何分阶段实施、把成果交给谁？**

交付入口：[AI 方案决策工作台](../mission-studio.html)。

本轮是**规则匹配的决策辅助产品**，不是 LLM，也没有在用户浏览器里调用真实第三方 Skills/Agents/MCP。使用者不需要 GitHub、Python 或注册便可以完成完整的“需求 → 候选 → 风险 → 组合 → 复核导出”流程。

## 真实能力及数据出处

| 功能 | 具体工作行为 | 来源/边界 |
|---|---|---|
| 自然语言目标归类 | 中文/英文关键词映射至教育、金融、增长、内容、工程、安全六大场景；也可手动指定 | \`mission-engine.js\` 可审计本地规则，无 LLM 语义理解 |
| 项目候选匹配 | 在 \`data/curated.json\` 的 133 条已核查仓库中排序，展示场景主题、项目描述、用途和实际目标词命中原因 | 规则场景相关度 0–100，仅用于本目录内部排序；不是性能评分 |
| 研究证据覆盖 | 根据编辑精选存在、Top 30 官方 README 研究、immutable Blob SHA、GitHub 最近推送快照等确定性指标计算 | 原 \`data/research_briefs.json\` 和 \`data/repo_metadata.json\`；必须显示上游官方仓库 |
| 安全与风险阻断 | 按元数据标记 unknown 许可证、archived、过期维护、目录高风险；所有候选缺少完整安全与商用许可审查，均明确展示阻断 | 不把 SPDX ID 当法律许可审查通过 |
| 多项目比较 | 最多选取五个仓库，比较研究证据、维护快照、风险与许可，不对价格、可用性、性能做无来源假设 | 最多五个只是交互上限，不是建议同时采用五个 |
| 实施蓝图编排 | 根据业务场景形成四阶段：输入定义、工具选型/数据处理、隔离测试、独立验收；允许人工选择各阶段候选仓库 | 阶段工具分配只是**拟定研究计划**，不证明接口兼容或实际串接 |
| 可复用与交接 | 可导出包含 blocker、approval 和 source 的 JSON/Markdown；浏览器本地保存最多十份计划 | localStorage 非账号/云存储，清理缓存可能丢失 |
| 手机端 | 支持手机浏览器使用，结果卡片与方案编辑区自动改为单列 | 由真实 Chrome 390px/768px/1440px 做可见性与无溢出检查 |

## 评分模型：不能偷换评价概念

场景匹配分 \`fit\` 主要来自 topic/type、与具体目标/场景关键词的重叠和 Atlas 编辑优先级，范围限制为 0–100。**没有经过有标签相关性数据集的 NDCG/Recall 验证**，因此是可解释初筛而不是可以证明最佳的软件推荐。

研究证据覆盖 \`evidence.total\` 有明确上限：编辑选入 10；Top 30 官方来源研究 20；可验证 Git Blob SHA 10；快照时点最后推送新鲜度最高 20；另有一个明确区分的 Docling 独立上游组件隔离运行证据最高 25。所有第三方软件**商业许可和完整安全审查均记 0**，最多理论只能 85。即使分数高也**不代表工作流集成、安全部署或许可放行**。

项目更新日期来自固定公开快照，**不是实时 GitHub 数据**。Top 30 官方来源档案来自已有桌面研究，项目名称和官方 URL 原样引用，不会填造新的项目来源。

## 对使用者的重要限制

- 输入框的业务目标只在当前浏览器处理；点击保存才保留在当前 localStorage。不要输入机密客户资料、私人 API Key、帐号密码或交易账户数据。
- 工具列出的 SPDX 元数据只是一条仓库快照；任何实际使用仍需审查许可证文本、特定版本、依赖许可和所在司法辖区。
- 方案导出状态始终是 \`RESEARCH_PLAN_NOT_EXECUTED\`，每一个真实业务环节必须有单独安全审批、合规审核、独立试验和回滚计划。
- 不发送真实营销私信、课程学生信息、金融交易订单；不部署真实第三方 SDK，不运行不可信代码，不访问浏览器其他网站。
- **真正的自主 AI Agent 是下一条独立研发线**：须建设可信服务器端、OIDC/多租户 RBAC、敏感数据治理、工具授权与确认、商用许可证审查、工作流执行沙盒、配额成本与审计。不能把当前静态 GitHub Pages 宣传为具备这些能力。

## 复现与发布门禁

无需付费模型或 SDK，可以使用 Node 24 运行纯函数测试：

\`\`\`bash
node --check mission-engine.js
node --test tests/mission-engine.test.cjs
\`\`\`

集成验证通过 \`scripts/build_site.py\`，将 \`mission-studio.html\` 与 \`mission-engine.js\` 纳入正式 Pages 文件清单，并在 \`deployment.json\` 标出 133 个编辑候选、30 个来源档案和第三方集成 0。

真实 Chrome 测试 \`tests/deployed-smoke.cjs\` 检查三种分辨率、改变目标是否重算、工具选择是否影响计数、已选工具比较、保存与重新打开、隐私及风险门禁、首页可达性。CI 中任何失败都将阻止合并；合并后必须再次通过 Pages 线上 smoke test。

## 下一研究阶段：真正超越规则匹配

本轮解决用户选型与沟通，不解决实际跨工具执行。应选择一个由真实访谈验证的场景，在授权、零真实用户数据条件下接入**实际开源组件**进行隔离集成，建立真实使用反馈、任务成功率、失败样本、人工耗时和成本的比较数据。只有验证之后，才逐步建设后端模型服务与多租户工作流；而不是继续用更多合成演示替代真实产品价值。
